02

단계별 런북 — Phase 0 → 6

카드를 클릭하면 세부 작업이 펼쳐집니다

P0사전 결정T-2주▶
  1. 타깃 리전 확정 (ap-northeast-2 유지) — 변경 시 Java 하드코딩 4곳 수정
  2. prod Terraform state 위치 확정·백업 (로컬이면 최우선 리스크)
  3. 도메인 전략 결정 (Pattern A 채택), milkyway.pe.kr 동반 이전
  4. 개선 확정: Multi-AZ, NAT+private subnet, 비밀 분리, OIDC, SSM 이관
  5. 3rd-party 콘솔 화이트리스트 목록화 (Google/Discord/Slack/Polar/Toss)
  6. DB의 절대 S3/CloudFront URL 저장분 감사
P1새 계정 부트스트랩 & 쿼터T-10일▶
  1. 서비스 쿼터 증설 조기 신청 (EC2 vCPU, EIP, VPC, RDS, CloudFront)
  2. 리전 가용성 확인 (EB solution stack, postgres 15.10, redis7, t4g)
  3. SCP가 리전/IAM/TF 리소스를 막지 않는지 확인
  4. 새 state 버킷 + 잠금 테이블 사전 생성 (bootstrap/state-backend)
  5. RDS용 CMK 생성 → TF kms_key_id에 미리 기입
  6. GitHub OIDC 설정 + 최소권한 IAM 역할
  7. 비밀값 SSM SecureString로 이관 + dev/prod 분리된 신규 값 생성
P2무중단 스테이트리스 스탠드업T-5일▶
  1. backend를 새 state 버킷으로 → terraform init -reconfigure (클린)
  2. apply 스테이트리스: VPC, SG, ElastiCache(빈), EB(빈), CloudFront, 프론트 버킷
  3. DNS Pattern A: 구 계정에 크로스계정 role 적용 → dns_account_role_arn 주입
  4. ACM 발급 — 검증 CNAME을 구 계정 기존 영역(이미 권한)에 기록 → 즉시 통과
  5. 새 첨부 버킷 생성 → ARCHIVE 객체 복원(3~5h) → 초기 aws s3 sync
  6. 컷오버 24~48h 전: 구 영역 레코드 TTL을 60s로 하향
  7. CloudWatch 알람 추가 (RDS/EB/Lambda) — 현재 전무
P3데이터 이전 — 컷오버 윈도우쓰기 동결▶
⏸ 쓰기 동결 시작 — 여기서부터 다운타임(30~60분)이 발생합니다
  1. 유지보수 모드 / 구 EB ASG → 0 (쓰기 중단). 구 infra-scheduler 비활성
  2. 첨부 버킷 최종 델타 sync
  3. 구 kanban-dev-db 최종 스냅샷 → CMK 재암호화 → 공유 → 새 계정 copy → restore → import
  4. engine_version=15.10 고정 + auto_minor_version_upgrade=false · 행수/체크섬 검증
  5. (선택) db_password 로테이션 후 SSM·EB 동시 갱신
  6. 새 EB → 복원 DB + 새 Redis + 새 첨부 버킷 지정 → 배포 → jwt_secret 로테이션 → health 체크
  7. Redis 데이터 이관 금지 (신규 빈 클러스터, DB에서 자동 복구)
P4DNS 컷오버 & 프론트 배포~60초 롤백▶
  1. NS 재위임 없음 (Pattern A) — apex/www/api alias 레코드를 새 CloudFront/ALB로 교체(TTL 60s) → 구 계정 state에서 state rm
  2. 프론트 CI 배포 + CloudFront /* 무효화 (GitHub vars 선갱신)
  3. ACM 검증 완료(ISSUED) + EB HTTPS 리스너·보조 인증서 부착 확인
P5컷오버 후 검증서비스 재개▶
  1. GitHub Secrets/Variables 갱신 (OIDC ARN, API_URL, CloudFront ID, RDS id, 비밀)
  2. E2E 스모크: OAuth 로그인 · 파일 업/다운 · WebSocket 동기화 · FCM 푸시 · 결제 웹훅
  3. CloudWatch 로그/메트릭/모니터링 Slack + 신규 알람 확인
  4. 비용 할당 태그 활성화
  5. infra-scheduler 동작 확인 + prod RDS 야간 정지 적용 여부 결정
P6구 계정 폐기1~2주 후▶
  1. 검증 완료까지 구 계정 read-only 유지 (DB 무손상, deletion_protection on)
  2. 최종 스냅샷 보관 후 구 DB 삭제 → 첨부/프론트 버킷·CloudFront·EB·state 삭제 (전역 이름 회수)
  3. 구 CI IAM 키·임시 admin 폐기, 잔존 공유 비밀 로테이션
  4. 디스크 잔여 산출물(deploy.zip, .jar)·.env·tfvars 정리
ℹ구 계정은 완전 폐기하지 않음 — Route53 영역(≈$0.5/월) + 크로스계정 IAM 역할 1개는 상시 유지(Pattern A 결정사항).

04

리소스별 이전 전략

섹션 4 요약

리소스전략처리
🗄️RDS CMK 재암호화 → 스냅샷 공유 → 복원 → import. 20GB면 pg_dump/restore도 실용적 이동
📦S3 첨부 새 이름 생성 → 교차계정 read → sync. ARCHIVE 객체 사전 복원, temp/ 제외, 절대 URL 감사 이동
📦S3 프론트 CI 재배포로 복구 가능 — 이름 충돌만 주의 재배포
⚡ElastiCache 데이터 비영속 → 빈 클러스터 신규 생성. 콜드 캐시·WS는 DB에서 자동 복구 신규(빈)
🔐CloudFront+ACM 인증서 재발급(이전 불가) + 배포 재생성. 보조 도메인 재부착 재발급
🌐Route53 Pattern A — 영역 구 계정 유지, aws.dns로 레코드만 크로스계정 관리, state rm으로 소유권 이양 구계정 유지
🔑비밀값 jwt 로테이션(전체 재로그인) + dev/prod 분리 + SSM/Secrets Manager 이관 로테이션

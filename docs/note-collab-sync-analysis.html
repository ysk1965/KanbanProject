두 창 모두 편집 모드이고, 양쪽 헤더에 프레즌스 아바타(상건·상건)가 둘 다 떠 있습니다. 이는 WebSocket 연결 · 룸(noteId) 조인 · awareness 릴레이가 정상 작동 중이라는 뜻입니다. 같은 릴레이 경로(relayToOthers)를 쓰는데 커서/프레즌스는 오가고 본문(Y.Doc)만 안 맞는다는 것은, 문제가 "네트워크 전송"이 아니라 문서의 초기 하이드레이션(seeding)과 적용 로직에 있음을 가리킵니다.

1아키텍처 요약 — 이중 저장소가 근본 배경

노트 본문은 서로 다른 두 곳에 저장됩니다. 이 이중 구조와 그 사이의 "수동 단방향 동기화"가 모든 문제의 뿌리입니다.

저장소내용소유 채널언제 갱신
notes.content
TEXT (BlockNote JSON)		 발행 스냅샷 — VIEW 모드가 보는 것 REST PUT 사용자가 "저장" 클릭 시에만
note_collab_states.yjs_state
byte[] (Yjs CRDT)		 라이브 드래프트 — EDIT 모드 실시간 상태 WebSocket /ws-collab/{noteId} 1.5초 디바운스 / 30초 주기 자동

서버는 CRDT 병합을 하지 않습니다. Yjs 상태를 불투명 blob으로 릴레이·저장만 합니다 (NoteCollabService.java:69 — "no server-side CRDT"). 병합 책임은 전적으로 클라이언트(Yjs)에 있습니다.

초기 문서를 Yjs 프로토콜로 받지 않습니다. 표준 y-websocket의 sync step1/step2(stateVector 교환)가 없고, 접속 시 서버가 무조건 MSG_SYNC_FULL(전체 상태)을 push합니다(NoteCollabHandler.java:113-162). 그리고 그 상태가 비어 있으면 각 클라이언트가 REST note.content를 자기 Y.Doc에 직접 주입합니다. 바로 여기서 사고가 납니다.

2원인 ① 이중 하이드레이션 → 본문 중복/분기 치명적 버그

초기 문서를 서버가 한 번만 시딩하는 게 아니라, 각 클라이언트가 각자 REST content를 Y.Doc에 replaceBlocks로 삽입합니다. 가드는 "내 로컬 에디터가 비어 있을 때만 주입"인데, 이 검사는 onSynced 순간의 로컬 스냅샷만 봅니다.

// NoteEditor.tsx:571-614 (요약)
const unsubscribe = collaboration.provider.onSynced(async () => {
  if (initialContentLoaded.current) return;
  const isEmpty = /* 내 로컬 Y.Doc이 비었나? — 릴레이 지연은 못 봄 */;
  if (!isEmpty || !note.content?.trim()) { initialContentLoaded.current = true; return; }
  await loadIntoEditor(editor, note.content);  // ← REST content를 Y.Doc에 주입
});
// loadIntoEditor → editor.replaceBlocks(...) → y-prosemirror가 Y.Doc 삽입 연산으로 변환

충돌 시나리오 (서버 저장본이 아직 빈 새 노트)

1
사용자 A 진입 → 로컬 Y.Doc 비어 있음 확인 → replaceBlocks(note.content) 주입. A의 clientID로 된 CRDT 연산 생성. MSG_SYNC_UPDATE 즉시 전송, full-state는 1.5초 뒤 전송.
2
1.5초의 창 동안 서버 storedState는 여전히 비어 있음 (UPDATE는 relay-only, 저장 안 됨).
3
이 창 안에서 사용자 B 진입 → B의 로컬 Y.Doc도 아직 비어 있음(A의 update 미반영) → B도 replaceBlocks(note.content) 주입.
4
B의 삽입은 A와 같은 텍스트지만 다른 Yjs itemID. CRDT는 dedupe하지 않고 둘 다 병합 → 본문이 통째로 2배 복제되거나, 타이밍에 따라 한쪽만 반영되어 분기.
서버가 MSG_SYNC_UPDATE를 릴레이만 하고 저장을 1.5초 지연시키는 설계(collabProvider.ts:43-47)가 이 충돌 창을 넓힙니다. 스크린샷처럼 한쪽은 비고 한쪽은 채워진 상태도, 이 하이드레이션 레이스의 한 결과(한 창은 주입, 다른 창은 "비었음" 판정을 놓쳐 미반영)로 설명됩니다.

근거: NoteEditor.tsx:571-644 · blocknoteContent.ts:142-173 · collabProvider.ts:225-230

3원인 ② EDIT ↔ VIEW 비대칭 설계상 제약

VIEW 모드 사용자는 Y.Doc을 아예 보지 않습니다. REST note.content(마지막 발행 스냅샷)를 정적 HTML로 렌더할 뿐입니다 (NoteEditor.tsx:552-561). 따라서:

  • 한 사람이 EDIT로 타이핑해도 상대가 VIEW면 실시간으로 안 보입니다.
  • 편집자가 "저장(발행)"을 눌러야 MSG_SNAPSHOT_UPDATED가 브로드캐스트되고, 그때서야 VIEW 창이 REST를 refetch합니다.
  • 즉 실시간 협업은 "양쪽 모두 EDIT 모드"일 때만 성립합니다.
사용자 입장에선 "저장 전까지 상대 화면에 아무것도 안 뜬다 = 동기화 안 됨"으로 느껴집니다. 이번 스크린샷은 둘 다 EDIT라 이 항목보단 원인 ①이 더 유력하지만, 평소 "동기화 안 되는 느낌"의 상당 부분이 이 비대칭에서 옵니다.

4원인 ③ 낙관적 락 부재 → 저장(발행) Last-Write-Wins 데이터 손실 위험

Note.java에 @Version 필드가 전혀 없고, PUT 요청에도 기대 버전/타임스탬프가 없습니다. 서버는 받은 content를 무조건 덮어씁니다.

// NoteService.java:216-221 — 충돌 감지 없음
if (request.getTitle() != null)   note.updateTitle(request.getTitle());
if (request.getContent() != null) note.updateContent(request.getContent(), user);
// @Retryable(:182)은 note_versions UNIQUE 충돌 재시도용일 뿐, content 충돌은 처리 안 함

두 사용자가 거의 동시에 저장하면 마지막 PUT이 승리합니다. 한쪽 화면이 미수렴 상태(직전 keystroke 미반영)에서 저장하면 그 스냅샷이 이겨 상대 편집이 발행본에서 누락될 수 있습니다.

더 위험한 지점 — 발행이 진행 중인 드래프트를 삭제

A가 저장하면 deleteState(noteId) + NoteDraftDiscardedEvent로 룸의 storedState=null + 리플레이 버퍼를 clear합니다 (NoteService.java:237-241 → NoteCollabHandler.java:263-272). 이때 B가 여전히 EDIT 중이면 B의 다음 1.5초 자동저장이 삭제된 드래프트를 되살려 발행본과 드래프트가 재분기합니다. 폐기(discard)에는 "다른 편집자 있으면 차단" 가드가 있지만(NoteEditor.tsx:971-986), 저장(발행) 경로엔 그 가드가 없습니다.

5원인 ④ 다중 인스턴스 — Redis 미설정 시 완전 분리 배포 환경 의존

인스턴스 간 브로드캐스트는 Redis Pub/Sub인데 조건부입니다. 기본값이 simple(in-memory)이라 명시 설정이 없으면 단일 인스턴스에서만 동작합니다.

# application.yml:181
app.websocket.broker-type: ${WS_BROKER_TYPE:simple}   # ← redis 아니면 in-memory 릴레이
Elastic Beanstalk에서 인스턴스가 2대 이상 + sticky session 없음 + WS_BROKER_TYPE≠redis이면, 두 편집자가 서로 다른 인스턴스에 붙었을 때 UPDATE/awareness가 아예 안 오갑니다. 각 인스턴스의 rooms·storedState가 영구 분기합니다.
단, 이번 스크린샷은 awareness가 양쪽에 보이므로 이 케이스는 아닙니다 — 같은 인스턴스(또는 Redis 정상)입니다. 그래도 프로덕션 다중 인스턴스에서 재현되는 별개 원인이므로 반드시 확인하세요.

추가: publishToRedis는 UPDATE/AWARENESS에서만 호출되고 SYNC_FULL 저장은 로컬 storedState만 갱신(NoteCollabHandler.java:195-206) → 인스턴스별 storedState 불일치 가능.

6원인 ⑤ relay-only + 지연 저장으로 인한 편집 유실 경합

  • MSG_SYNC_UPDATE는 릴레이만 되고 서버에 저장 안 됨. 늦게 접속한 클라이언트는 마지막 full-state까지만 받음.
  • 편집자가 저장 없이 하드 디스커넥트하면 최대 1.5초~30초 편집분이 서버에 없어 다음 접속자에게 누락 가능.
  • 모든 세션이 나가면 룸과 pendingUpdates 버퍼가 통째 제거 → 마지막 auto-save 이후 in-flight 증분 소실.

7원인 우선순위 종합

#원인이번 증상 연관도성격
①이중 하이드레이션(각 클라가 REST content를 각자 주입) → 중복/분기매우 높음버그
②EDIT↔VIEW 비대칭 (VIEW는 라이브 미수신)중간 (둘 다 EDIT라 이번엔 아님)설계
③낙관적 락 부재 → 발행 LWW · 진행 중 드래프트 삭제 레이스높음버그/설계
④다중 인스턴스 Redis 미설정이번엔 배제 (awareness 정상)배포
⑤relay-only + 지연 저장 유실중간경합
이번 스크린샷의 가장 유력한 원인은 ①입니다. awareness는 오가는데 본문만 안 맞고 한쪽이 비어 있는 상태는, "각 클라이언트가 초기 문서를 스스로 시딩하는" 구조에서 하이드레이션 가드가 릴레이 지연 창을 못 보고 어긋난 전형적 결과입니다. 근본 치료는 초기 시딩을 클라이언트가 각자 하지 않게 만드는 것입니다.

8권장 해결 방향

Fix 1. 서버 측 1회 시딩 (권장·근본)

클라이언트가 replaceBlocks(note.content)로 초기 문서를 넣는 방식을 폐기하고, 서버가 룸 최초 생성 시 note.content를 Yjs state로 변환해 storedState에 한 번만 시딩합니다. 이후 모든 클라이언트는 순수 Yjs sync로만 문서를 받습니다.

→ 원인 ① 완전 제거. 단, BlockNote JSON ↔ Yjs state 변환을 서버(또는 공유 seeding 클라 1명)에서 수행해야 함.

Fix 1-lite. 리더 선출 하이드레이션 (경량)

서버가 룸의 첫 접속자에게만 "시딩 권한" 플래그를 내려주고, 나머지는 절대 replaceBlocks하지 않게 합니다. MSG_SYNC_FULL 헤더에 isSeeder 1바이트 추가로 구현 가능.

→ 서버 변환 없이 원인 ① 차단. 가장 적은 변경으로 즉효.

Fix 2. 하이드레이션 가드 강화

onSynced 로컬 스냅샷 대신 서버가 "storedState가 실제로 비었다"고 확정한 신호가 있을 때만, 그리고 그 순간 내가 유일한 접속자일 때만 주입하도록 조건을 좁힙니다.

Fix 3. 저장 낙관적 락

Note에 @Version 추가 + PUT에 expectedVersion 전달. 충돌 시 409 반환 → 프론트 머지 프롬프트. 최소한 발행 경로에도 "다른 편집자 있으면 확인" 가드 추가(폐기 경로와 동일).

Fix 4. VIEW 실시간화(선택)

VIEW 모드도 Yjs 문서를 read-only로 구독해 라이브 반영. 현재의 "스냅샷 격리"를 유지하려면, 최소한 상대가 편집 중일 때 "편집 중 · 저장 시 갱신" 배너를 명확히 노출.

Fix 5. 다중 인스턴스 확정

프로덕션에서 WS_BROKER_TYPE=redis 설정 확인, 또는 로드밸런서 sticky session 적용. 배포 환경에서만 재현되는 협업 실패의 대비책.

가장 빠른 실전 순서: ① Fix 1-lite(리더 선출 시딩)로 본문 중복/분기부터 잡고 → ② Fix 3의 발행 경로 편집자 가드로 저장 시 손실을 막은 뒤 → ③ 프로덕션 Redis/sticky를 점검하는 것을 권합니다.

  • 단일 인스턴스 재현: 로컬에서 새 노트를 두 탭으로 동시에 EDIT 진입 → 한쪽에 타이핑 → 다른 쪽 반영/중복 여부 확인. (원인 ① 격리)
  • DevTools Network → WS 프레임: 두 탭에서 /ws-collab/{noteId} 연결 여부, MSG_SYNC_UPDATE(type 1) 프레임이 상대에게 relay되는지 확인.
  • 중복 확인: 저장 후 note.content JSON에 같은 블록이 2배로 들어갔는지 확인(원인 ① 확정 증거).
  • 프로덕션: WS_BROKER_TYPE 환경변수 값, EB 인스턴스 수, ALB sticky session 설정 확인.
  • CORS: 배포 도메인이 NoteCollabWebSocketConfig.java:29-44 화이트리스트(FRONTEND_URL 등)에 있는지.

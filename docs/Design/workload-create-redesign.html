워크로드 「새 업무 추가」 개선안

대상: ScheduleResourceView 드래그 → WorkloadCreateModal · 2026-07-29 · 문제: 피쳐/태스크/체크리스트 중 어디에 넣어야 하는지 판단 부담

01

지금 무엇이 어려운가

현재 모달은 "무엇을 할지"보다 "어디에 넣을지"를 먼저 묻는다
간트 드래그→ 마일스톤?→ Feature?→ Task?→ 제목 입력→ 추가

사용자가 아는 것은 "○○ 작업을 이 기간에 넣고 싶다" 하나뿐인데, 모달은 그걸 적기 전에 계층 3개를 먼저 결정하라고 요구한다. 게다가 실제로 만들어지는 것은 체크리스트 항목인데, 모달 어디에도 그 단어가 없어서 자신이 무엇을 만드는지조차 알 수 없다.

P1 순서가 거꾸로다

제목 입력창이 맨 아래에 있다. 자동 포커스는 제목에 가 있는데 시선은 위 드롭다운 3개에 붙잡힌다. "미분류로 그냥 넣을까?"를 매번 고민하게 만든다.

P2 용어가 4겹인데 설명이 없다

마일스톤 · Feature · Task · (숨겨진) 체크리스트. 계층 관계를 모르는 멤버는 Feature와 Task 차이를 모달 안에서 배울 방법이 없다.

P3 전부 "(선택사항)" = 아무 안내도 아니다

세 필드 모두 선택사항이라 무엇이 권장인지 알 수 없다. 선택지는 많고 기본값은 없는, 전형적인 결정 피로 구조.

P4 "미분류에 추가됩니다"의 결과를 모른다

인박스에 쌓이면 나중에 누가 정리하는지, 스프린트/리포트에 잡히는지 알 수 없어 불안해서 오히려 아무거나 고르게 된다.

P5 검색이 없다

Feature/Task 드롭다운이 단순 목록이다. 보드가 커지면 스크롤로 찾아야 하고, Task 목록은 Feature를 고른 뒤에야 네트워크 요청으로 나타나 폼이 튄다.

P6 맥락을 하나도 안 쓴다

"누구의 행에서 · 어떤 기간을" 드래그했는지 이미 알고 있다. 그 사람이 지금 진행 중인 Task, 최근에 넣던 Feature — 서버가 답을 알고 있는데 사용자에게 되묻는다.

핵심 진단 — 이건 "드롭다운을 예쁘게 만드는" 문제가 아니라 결정 시점을 뒤로 미룰 수 있느냐의 문제다. 배치(placement)는 생성 시점에 반드시 필요한 정보가 아니다. 서버는 이미 feature_id/task_id가 없으면 인박스로 보내고, Feature만 있으면 Task를 자동 생성한다 (ChecklistService.resolveTargetTask). 기술적으로는 이미 "나중에 정해도 되는" 구조인데 UI만 그걸 숨기고 있다.
02

설계 원칙 5

원칙내용
① 내용 우선제목을 먼저 받는다. 배치는 제목 아래에서 추천으로 제시한다. 사용자가 첫 화면에서 결정해야 할 것은 0개.
② 결정 대신 확인드래그 맥락(담당자·기간·마일스톤)으로 배치 후보를 서버가 랭킹해서 준다. 사용자는 고르는 게 아니라 맞는지 확인만 한다.
③ 계층은 결과로 보여준다선택 UI를 3개 두는 대신, 최종 경로 한 줄(마일스톤 › Feature › Task › 내 업무)을 항상 보여준다. 계층 학습이 부수 효과로 일어난다.
④ 인박스는 실패가 아니라 정식 경로"미분류에 추가됩니다"(불안) → "인박스에 담아두고 나중에 정리"(의도적 선택). 되돌릴 수 있음을 명시.
⑤ 고급 경로는 접어둔다마일스톤/Feature/Task 직접 선택은 [경로 변경] 안에서만. 통합 검색 하나로 3계층을 동시에 찾는다.
03

개선안 3종 비교

A는 즉시 적용 · B는 A의 하위 구성요소 · C는 대량 편집용

A. 스마트 배치 추천

제목 먼저 + 배치 추천 칩 3개 + 경로 프리뷰 한 줄. 상세 선택기는 [변경] 뒤로.

결정 수 3 → 0~1

B. 통합 검색 (Command Palette)

필드 하나에서 Feature·Task를 함께 검색. 결과가 계층으로 표시되고, 없으면 "새로 만들기"가 같은 리스트에 뜬다.

결정 수 3 → 1
공수 FE 中 · BE 小(검색 API 1개)
→ A의 [경로 변경] 화면으로 채택

C. 3열 컬럼 브라우저

마일스톤 | Feature | Task 를 좌→우 3열로. 계층은 가장 명확하지만 모달이 커지고 모바일에서 무너진다.

결정 수 3 → 3(단, 시각적)
공수 FE 大
→ 보류 (대량 정리용 별도 화면에 적합)

결론 — A를 본 플로우로 채택하고, A의 [경로 변경] 내부를 B로 구현한다. 여기에 0-클릭 경로(§5 인라인 퀵애드)를 더해 "그냥 빨리 넣고 싶다"는 케이스를 모달 없이 처리한다.

배치 추천 로직

신규 API 1개 — 상위 3건 + 인박스

GET /api/v1/boards/{boardId}/workload/placement-suggestions?assignee_id&contractor_id&start_date&due_date

순위신호규칙뱃지
1진행 중 Task같은 담당자에게 배정된 Task 중 상태 IN_PROGRESS 이고 기간이 드래그 구간과 겹치는 것 (겹침 일수 내림차순)진행 중
2최근 사용같은 담당자가 최근 14일 내 체크리스트를 추가한 Task (최신순, 최대 2건)최근 사용
3이번 마일스톤드래그 시작일을 포함하는 마일스톤(최단 구간 우선)의 Feature 중 해당 담당자 Task 보유 수 상위 → Task는 자동 생성이번 마일스톤
4보드 최근위로 3건이 안 차면 보드 전체에서 최근 활동한 Feature로 채움최근 활동
—인박스항상 마지막 고정. 후보가 0건이면 인박스가 기본 선택기본
기본 선택 규칙 — 1순위 후보가 있으면 그것을 미리 선택(pre-select)한다. 없으면 인박스를 선택한 상태로 연다. 어떤 경우에도 "선택 안 됨" 상태로 열리지 않는다.

응답 형태 (snake_case)

필드설명
suggestions[].kindTASK | FEATURE | INBOX — FEATURE면 서버가 Task 자동 생성
suggestions[].task_id / feature_id그대로 POST /checklist-items/from-workload 에 전달
suggestions[].path{milestone_title, feature_title, feature_color, task_title} — 경로 한 줄 렌더용
suggestions[].reasonIN_PROGRESS | RECENT | CURRENT_MILESTONE | BOARD_RECENT — FE가 뱃지 문구로 매핑
기존 생성 API는 그대로 쓴다. ChecklistService.resolveTargetTask 가 이미 task_id → feature_id → new_feature_title → 인박스 순으로 처리하므로 백엔드 생성 로직 변경 없음. 추가되는 것은 조회용 추천 API 1개와 Feature/Task 통합 검색 API 1개뿐이다.

구현 계획

3단계 — 각 단계가 독립적으로 배포 가능

Step 1 — 모달 재배열 (BE 변경 없음) 즉시

  • 제목 입력을 최상단으로 이동, 자동 포커스 유지
  • 마일스톤·Feature·Task 드롭다운 3개를 경로 한 줄 + [변경]으로 접기
  • 마이크로카피 §7 전면 반영 (i18n/locales/*.json — schedule.workloadCreate.*)
  • 헤더에 담당자·기간 표기
  • 대상: frontend/src/app/components/schedule/WorkloadCreateModal.tsx

Step 2 — 통합 검색 + 추천 본편

  • BE: GET /boards/{id}/workload/placement-suggestions (§6)
  • BE: GET /boards/{id}/placement-search?q= — Feature/Task 동시 검색
  • FE: 추천 칩 목록 + [변경] → 검색 팔레트(↑↓/⏎ 키보드 내비게이션)
  • FE: utils/api.ts · utils/services.ts 에 API 추가

Step 3 — 인라인 퀵애드 확장

  • ScheduleResourceView: pendingCreate 시 모달 대신 바 내부 인라인 인풋 렌더
  • ⏎ = 인박스로 즉시 생성 / ⇥ = 모달 승격 / Esc = 취소
  • 생성 후 토스트 + [위치 지정] 액션

검증 지표

  • 드래그 → 생성 완료까지 걸리는 시간 (목표: 중앙값 절반)
  • 모달 이탈률 — 열고 나서 추가하지 않고 닫은 비율
  • 인박스 유입 비율 — 줄어들면 추천이 잘 맞는 것. 늘어나되 정리율이 높으면 그것도 성공
  • [변경] 클릭률 — 20% 미만이면 추천 랭킹이 충분히 정확

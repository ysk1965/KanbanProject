02

고장은 하나가 아니라 셋이 겹쳤다

필드 리네임은 방아쇠일 뿐이다. 한 발이 큐 전체를 세우고 후보를 영구히 태우는 위력을 갖게 된 것은 아래 2·3번 때문이고, 이쪽은 리네임을 되돌려도 그대로 남는다.

문제 ① 계약 드리프트
서버 DTO가 리네임됐는데 맥의 스크립트는 손으로 배포된다. 두 쪽을 묶는 장치가 없다.
문제 ② 회신 없는 조기 종료
명세 검증 실패가 trap cleanup EXIT 설치 전이라, 콜백 없이 죽는다. 서버는 영원히 기다린다.
문제 ③ 되살릴 수 없는 TIMED_OUT
회수된 작업은 CANCELLED로 만들 경로가 없고, 가드레일은 그 이슈를 영구 제외한다.

① 서버가 보내는 것 vs 러너가 읽는 것

커밋 f963c23f(자동수정 수동 위임)에서 큐가 JIRA 전용이 아니게 되면서 RunnerJob이 일반화됐다. 맥에 설치된 스크립트는 그 직전 버전(3adfc117)과 바이트 단위로 동일하다.

의미 서버가 보내는 키 (develop) 러너가 읽는 키 (설치본) 결과
작업 식별자 job_key jira_issue_key 빈 값 → 즉시 종료
작업 종류 (JIRA / 수동 위임) job_kind — 없음 무시됨

대상 저장소 · 브랜치 · 상한 repo_full_name · base_ref · branch · timeout_minutes 동일 일치
회신 페이로드 job_key (issue_key도 계속 수용) issue_key 호환됨 — 콜백은 문제 없다

주의할 대칭: 회신(콜백) 방향은 서버가 구버전 키를 계속 받아주도록 배려돼 있다. 정작 깨진 것은 배려가 없는 반대 방향, 즉 claim 응답이다. 한쪽만 하위호환을 챙기면 "호환을 신경 썼다"는 인상만 남고 사고는 그대로 난다.

② 왜 서버는 실패를 몰랐나 — 가드가 트랩보다 앞에 있다

③ 한 번 회수되면 그 이슈는 다시 큐에 담기지 않는다

판정조건이 상황에서
재투입 가능 여부 existsActiveForIssue: status ≠ CANCELLED TIMED_OUT은 "이미 처리함"으로 센다 → 후보에서 빠진다
취소 cancel(): status == QUEUED 해당 없음

즉 서버가 자동 회수하기 전에 사람이 도크에서 "강제 회수"를 누르면 살아나고, 놓치면 그 이슈는 DB를 직접 손대기 전까지 자동수정 대상에서 영구히 사라진다. 회수는 "러너가 죽었다는 추정"이지 사실 확인이 아닌데, 추정 한 번이 되돌릴 수 없는 결과를 만든다.

03

무엇을 고치면 무엇이 달라지나

A는 지금의 정지를 푸는 응급 조치, B·C는 같은 사고가 다시 나도 큐가 멈추지 않게 하는 구조 변경, D는 이미 태워진 후보를 되살리는 경로, E는 애초에 계약이 어긋나지 않게 하는 예방이다.

지금적용됨

A. 러너 스크립트를 배포본과 동기화

약 2분 · 무중단
지금
받아든 명세를 해석하지 못해 모든 작업이 즉시 실패. 큐가 90분 주기로 봉쇄된다.
적용 후
job_key·instruction을 읽어 즉시 정상 처리 재개. 수동 위임 작업도 함께 받는다.

  > ~/bridge-autofix/autofix-once.sh
git -C ~/orca/KanbanProject show origin/develop:tools/autofix/runner/bridge-autofix-runner.sh \

runner.conf는 새로 필요한 키가 없어 그대로 쓴다. verify-compile.sh는 이미 최신과 동일하다. 단, 이 조치만으로는 재발을 못 막는다 — 다음 리네임 때 똑같이 반복된다.

구조적용됨

B. claim 응답에 계약 버전을 싣고, 불일치면 러너가 스스로 신고한다

서버 소폭 + 러너 10줄
지금
불일치가 빈 문자열로 나타난다. 로그에 "키가 없다" 한 줄이 남을 뿐, 서버·슬랙·화면 어디에도 신호가 없다.
적용 후 (구현됨)
서버가 작업을 내주기 전에 거절한다(CONTRACT_MISMATCH). 큐는 그대로 남아 아무것도 타지 않고, 러너 로그와 도크가 "러너 v2 / 서버 v3 — 스크립트를 다시 배포하라"를 명령어까지 붙여 보여준다.
  • 러너가 claim 요청에 contract_version을 실어 보낸다 (RUNNER_CONTRACT=3)
  • 서버는 AutofixRunnerContract.VERSION과 대조해 다른 판정보다 먼저 거른다 — 낡은 러너에 내주면 그 건은 반드시 타기 때문이다
  • 마지막으로 받은 러너 버전을 저장해 도크가 연결됐는데 왜 안 도는지를 스스로 설명한다
  • 남은 것: 슬랙 알림. 계약 불일치는 러너가 살아 있는 고장이라 기존 "러너 무응답" 알림에 걸리지 않는다 — 별도 스로틀 상태가 필요해 이번에는 넣지 않았다
구조적용됨

C. "어떤 경로로 끝나든 회신한다"를 실제로 성립시킨다

러너 수 줄 이동
지금
트랩 설치 이전(설정 로딩·명세 검증·PROJECT_DIR 확인)에서 죽으면 서버는 90분을 기다린다.
적용 후
어떤 조기 종료도 즉시 failed로 회신. 봉쇄 시간이 90분 → 수 초로 줄고, 실패 사유가 화면에 남는다.
  • 1안: trap cleanup EXIT를 명세 파싱 직후로 올리고, 검증 실패를 fail()로 처리
  • 2안(더 튼튼함): 폴링 루프가 autofix-once.sh의 종료 코드를 보고, 회신 흔적이 없으면 루프가 대신 failed를 보낸다 — 자식이 어떤 이유로 죽든(문법 오류·SIGKILL 포함) 커버된다
  • 둘 다 하면 좋다. 2안은 스크립트를 갈아끼우다 생긴 문법 오류까지 막아준다
복구적용됨

D. 회수된 작업을 다시 큐에 담을 수 있게 한다

서버 소폭 + 도크 버튼 1개
지금
TIMED_OUT은 취소도 재투입도 안 된다. 러너 쪽 사고 한 번에 후보 이슈가 영구 소각된다.
적용 후
도크에서 "다시 시도" 한 번으로 되살아난다. 러너를 고친 뒤 태워먹은 건들을 일괄 복구할 수 있다.
  • cancelJob(force)가 TIMED_OUT·FAILED도 CANCELLED로 내릴 수 있게 허용 — 가드레일(existsActiveForIssue)은 손대지 않는다
  • "이슈당 1회"의 취지는 중복 PR 방지이지 사고 시 영구 배제가 아니다. PR이 실제로 열린 SUCCEEDED는 지금처럼 잠가 둔다
예방적용됨

테스트 1개

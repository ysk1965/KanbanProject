Milkyway · 스프린트 뷰 개념 UX 제안

명사가 다섯 개다.
질문은 세 개면 된다.

마일스톤·스프린트·피처·태스크·체크리스트. 처음 온 사람이 이 화면에서 배워야 할 개념이 다섯 개고, 거기에 블록 보드의 컬럼까지 여섯 개다. 개념을 줄이자는 얘기가 아니다 — 다섯 개를 세 개의 질문에 나눠 담고, 필요할 때만 꺼내 보이자는 얘기다.

현재 노출 개념 6 첫 화면 목표 2 보드 내 이동 가능 뷰 17 태스크 한 장의 좌표 5

진단 / 카드 한 장의 좌표

문제는 개념 개수가 아니라, 카드 하나가 다섯 군데에 동시에 있다는 것

tasks 테이블 한 행이 들고 있는 외래키다. 이 중 하나만 봐도 카드 위치를 말할 수 없다. 신규 유저가 헷갈리는 건 "스프린트가 뭐지"가 아니라 "이 카드는 지금 어디 있는 거지"다.

튜토리얼 작업 (Sprint3) tasks · task_key = STORY-42
feature_id · NOT NULL 게임 플로우 작업 무엇을 위한 일인가
milestone_id · NULL 허용 4. 테스트런칭 어느 단계에 속하나
sprint_id · NULL 허용 Sprint 3 이번 주기에 담겼나
block_id · NOT NULL 개발 중 칸반 보드에서의 상태
sprint_column_id In Review 스프린트 보드에서의 상태
↑ 같은 카드가 칸반에서는 개발 중, 스프린트에서는 In Review다. 상태의 진실이 두 개고, 둘을 동기화할 규칙은 END 컬럼 도달 시 체크리스트 완료 하나뿐이다. 여기에 담당자는 카드가 아니라 checklist_items.assignee_id에만 있어서, 구성원 뷰에서는 같은 카드가 여러 컬럼에 동시에 서게 된다.

재구성 / 세 개의 축

다섯 개 명사를 "무엇 · 언제 · 어디"로 나눠 담는다

개념을 지우지 않는다. 이미 만들어 놓은 것들은 각자 이유가 있다. 대신 어느 질문에 답하는 물건인지를 UI 언어로 못 박으면, 외울 게 다섯 개에서 세 개로 줄어든다.

What

무엇을 위한 일인가

목적의 묶음. 시간과 무관하게 존재하고, 다 끝나면 사라진다.

  • Feature 묶음 — "이걸 왜 하나"
  • Task 작업 — 카드 한 장
  • Checklist 할 일 — 사람이 체크하는 최소 단위
When

언제까지 하는가

기간 상자. 작업을 담았다 비웠다 할 뿐, 스스로 일을 만들지 않는다.

  • Milestone 단계 — 몇 주~몇 달
  • Sprint 주기 — 단계 안의 반복
Where

지금 어디까지 왔나

흐름의 위치. 하나여야 한다 — 지금은 둘이라 이 축이 깨져 있다.

  • Column 컬럼 — 할 일 / 하는 중 / 끝
  • Block 중복 — 통합 대상

그리고 한 문장: 실제 "일"은 체크 한 줄뿐이다

담당자도, 완료 시각도, 완료한 사람도 전부 checklist_items에 있다. Feature·Task·Milestone·Sprint의 진행률은 전부 이 줄에서 파생된다. 이걸 UI에서 대놓고 말해주면 — "이 화면에서 당신이 실제로 하는 건 체크뿐입니다" — 나머지 네 개는 외울 개념이 아니라 서랍 이름이 된다.

보드 복잡도를 유저가 고르게 한다

1단계. 보이는 건 작업 카드와 그 안의 할 일뿐이다. 컬럼 이름은 상태가 아니라 동사다. 마일스톤·스프린트·묶음은 존재하지만 화면에 없다 — 데이터는 그대로 쌓이고, 나중에 켜면 그때 나타난다.

해결책 2 / 만들면서 배우기

개념 설명서 대신, 첫 스프린트를 같이 만든다

용어를 먼저 설명하면 아무도 안 읽는다. 실제 데이터를 만들게 하고, 방금 만든 것의 이름을 사후에 알려주는 순서로 뒤집는다. 4단계, 각 단계는 입력 하나.

해결책 3 / 반복 노출

카드 한 줄 브레드크럼이 개념 지도를 대신한다

도움말 문서는 한 번 읽히고 잊힌다. 위계를 카드마다 한 줄로 반복하면 유저는 설명 없이 구조를 학습한다. 칩에 마우스를 올리면 그 개념이 무엇인지 한 줄로 나온다.

› › › ›

색이 축을 말한다 — 청록 = 언제, 보라 = 무엇, 주황 = 실제 일. 같은 색 규칙을 필터 바·레일·컬럼 헤더에 그대로 쓰면, 유저는 색만으로 축을 구분하게 된다.

진단 / 과잉과 허점

UX 이전에 시스템에서 먼저 정리할 것

화면을 아무리 잘 만들어도, 아래 네 개가 남아 있으면 설명이 계속 필요하다.

치명 · 상태 이중화

컬럼 시스템이 두 벌이다

blocks(칸반 컬럼, 보드 단위)와 sprint_columns(스프린트 컬럼, 마일스톤 단위)가 각각 독립된 위치를 갖는다. 태스크는 block_id가 NOT NULL이라 스프린트에만 있고 싶어도 칸반 어딘가에 반드시 서 있어야 한다. "이 카드 상태가 뭐야"에 정답이 두 개인 구조다.

backend/…/block/Block.java · sprint/SprintColumn.java · task/Task.java (block_id NOT NULL + sprint_column_id)

제안: 스프린트 컬럼을 정본으로 삼고 블록은 그 위의 표시 그룹으로 강등한다. 중간 단계로는 최소한 "블록 보드"를 기본 숨김 처리하고, 마이그레이션 없이도 sprint_column_id가 있으면 그 값을 카드 상태로 단일 표기한다.

치명 · 담당자 부재

Task에 담당자가 없다

담당자는 features.assignee_id와 checklist_items.assignee_id에만 있고 tasks에는 없다. 그래서 구성원 뷰는 카드 한 장을 여러 컬럼에 복제해 놓고, 각 컬럼에서 "그 사람 몫만" 다시 계산한다 — 스크린샷의 2/2 · 전체 23/24, 담당 외 21개 같은 이중 표기가 그 증상이다. 신규 유저는 카드 하나의 진행률을 읽는 법부터 배워야 한다.

frontend/…/SprintBoard.tsx — lineOwnedBy() / memberCardDone() / "담당 외 N개"

제안: tasks.owner_id를 추가한다(체크리스트 담당자 중 최다 보유자로 자동 채움, 수동 변경 가능). 카드는 한 컬럼에만 서고, 세부 담당은 카드를 열었을 때만 보이면 된다. 진행률 표기가 한 줄로 줄어든다.

과잉 · 날짜 5층

같은 일에 시작·종료일이 다섯 벌 있다

Milestone(start/end) · Sprint(start/end) · Feature(start/due) · Task(start/due + baseline start/due) · ChecklistItem(start/due). 어긋나도 아무도 막지 않고, 어느 날짜가 진짜인지 화면마다 다르다. 입력 비용은 5배인데 신뢰도는 1/5이다.

milestone/Milestone.java · sprint/Sprint.java · feature/Feature.java · task/Task.java · checklist/ChecklistItem.java

제안: 사람이 직접 입력하는 날짜는 단계와 주기 둘만 남긴다. Feature·Task 날짜는 하위 항목에서 파생(min/max)해 읽기 전용으로 표시하고, 직접 입력이 꼭 필요할 때만 "직접 지정" 배지를 달아 예외로 드러낸다.

과잉 · 뷰 17개

보드 하나에 갈 수 있는 곳이 17군데다

상단 탭 5(보드·일정·회의·자료실·보고서) → 서브탭 4(대시보드·칸반·마일스톤·마인드맵) → 칸반 내 서브탭 3(스프린트·블록보드·JIRA) → 우하단 뷰 전환 5(칸반·리스트·간트·캘린더·미니칸반). 네 층의 내비게이션이 서로 다른 위치·다른 모양으로 존재한다. 처음 온 사람이 "메인 화면"을 못 찾는 건 당연하다.

frontend/…/BoardSubTabs.tsx · FloatingViewSwitcher.tsx · KanbanBoardPage.tsx(3,984줄)

제안: 스프린트 뷰를 유일한 기본 진입점으로 못 박고, 나머지는 같은 데이터를 다르게 보는 렌즈로 한 곳(우상단 단일 드롭다운)에 모은다. 블록보드는 복잡도 3단계에서만, 마인드맵·간트는 "보기 방식"으로 내린다.

허점 · 진입 순간

빈 보드에서 첫 클릭이 정해져 있지 않다

보드를 만들면 기본 마일스톤이 자동 생성되고(isDefault=true), sprintEnabled는 false다. 즉 신규 유저의 첫 화면은 "스프린트 뷰가 메인"이라는 의도와 달리 스프린트가 꺼진 상태다. 의도와 기본값이 어긋나 있다.

milestone/Milestone.java — sprintEnabled default false, isDefault 자동 생성

제안: 복잡도 1단계에서도 스프린트 프레임은 켜두되 이름만 감춘다 ("이번 주기" 헤더 없이 컬럼만). 온보딩 4단계를 마치는 순간 2단계로 자동 승급하고, 그때 처음 "스프린트"라는 단어를 보여준다.

실행 / 순서

싼 것부터, 되돌릴 수 있는 것부터

앞의 셋은 스키마를 건드리지 않는다. 효과를 보고 나서 뒤의 둘을 결정해도 늦지 않다.

카드 브레드크럼 + 개념 칩 툴팁 축별 색 규칙을 필터·레일·컬럼 헤더까지 확장. 문서 없이 위계가 학습된다.
FE only · 반나절
복잡도 3단계 게이팅 보드 설정 값 하나 + 조건부 렌더. sprintEnabled 토글을 일반화해 재사용.
FE + 컬럼 1개 · 1~2일

FE only · 2일
